# Crow Station — ملف تسليم التحليل والتخطيط للفريق

> الإصدار 0.2 · 29 أكتوبر 2026 · مرجع لاستكمال الأسئلة والقرارات · مرحلة تحليل فقط

## 1. ابدأ من هنا

**المطلوب من الفريق:** مساعدة صاحب المشروع في إكمال قواعد العمل والأسئلة المفتوحة، وتحويل الإجابات إلى متطلبات واضحة قابلة للمراجعة قبل تصميم قاعدة البيانات وواجهات API وخطة التنفيذ. لا يبدأ هذا التسليم البرمجة، ولا يجعل المقترحات قرارات معتمدة.

**نقطة الاستئناف الدقيقة — H-Q05:** كيف نحسب الاسترداد للكورس ذي الفيديو والنص والاختبارات، وما قيم الدروس المعتمدة؟ حُسمت H-Q01 إلى H-Q04 في 29 أكتوبر 2026؛ راجع القسم 4.3 و[بطاقات القرارات](DECISION-CARDS.ar.md).

**تنبيه بشأن المرجع الحالي:** وثيقتا المنتج وتخطيط البيانات في المستودع بالإصدار 0.2 بتاريخ 30 سبتمبر 2026. توجد إجابات لاحقة في المحادثة لم تُدمج فيهما بعد، ومنها إلغاء البيع الجزئي واستقلال سعر كل كورس. يجمع القسم 4 هذه القرارات، والقسم 5 يحدد مواضع التحديث المطلوبة. لا تستخدم النصوص القديمة المتعارضة كسياسة حالية.

اقرأ بالترتيب:

1. هذا الملف، خصوصاً القرارات الأحدث ونقطة الاستئناف.
2. [وثيقة المنتج](PROJECT-BRIEF.ar.md): الرؤية، النطاق، قواعد العمل والرحلات؛ مع تطبيق تصحيحات هذا التسليم.
3. [تخطيط البيانات](DATA-PLANNING.ar.md): كيانات وعلاقات مقترحة، وليست جداول معتمدة.
4. [سياسة الفروع](../BRANCHING.md) و[حالة المستودع](../REPOSITORY-STATUS.md).

## 2. المشروع وحدود المهمة

Crow Station منصة تعليمية موحّدة تجمع كورسات مالك المنصة والمدرسين الآخرين. يدخل الطالب إلى كتالوج واحد؛ لكل مدرس صفحته ولوحة واحدة خاصة به وفريقه. ليست أكاديميات مستقلة بنطاقات وهوية منفصلة لكل مدرس. وصف Multi-Tenant لا يحسم طريقة العزل التقني.

| المحور | الحالة الحالية |
| --- | --- |
| الجمهور | البرمجة والأمن السيبراني؛ العراق أولاً، مع السماح بالوصول من الخارج. الدفع يتبع الخدمات والاتفاقات المتاحة. |
| قنوات الاستخدام | موقع متجاوب وتطبيق موبايل، بواجهتين عربية وإنجليزية. |
| الفريق والموعد | صاحب المشروع مع فريق من 10 أشخاص بخبرات متوسطة في البرمجة والأمن السيبراني وأدوات AI؛ سبتمبر 2027 هدف إطلاق مبدئي قابل للمراجعة. |
| الحجم التخطيطي | نحو 1,000 مستخدم؛ توزيع المشاهدين ومشغلي الأكواد والمحادثات والحمل الفعلي يحتاج تفصيلاً. |
| التقنيات المتفق على اتجاهها | Clean Architecture، وASP.NET Core على .NET 10، وPostgreSQL، وFlutter للموبايل، وDocker وDocker Compose. |
| قرارات تقنية مفتوحة | واجهة الويب، العزل، MinIO أو بديله، تأكيد Redis ودوره، بث الفيديو والبحث وتشغيل الكود ومزوّد AI والتشغيل الإنتاجي. |
| المطلوب الآن | إجابات وقواعد عمل، وسجل قرارات، ومصفوفة صلاحيات، ثم نموذج منطقي وعقود API وخطة تنفيذ بعد استقرار المتطلبات. |
| غير المطلوب الآن | برمجة المنتج، إنشاء جداول أو ترحيلات نهائية، إطلاق بيئات إنتاج، أو اختيار مزوّدين بلا مراجعة. |

نطاق النسخة الأولى واسع: الحسابات، المدرسون، الكورسات، الدفع والمحافظ، الفيديو والتقدّم، المحرر على الحاسوب، الاختبارات والتصحيح والشهادات، محادثة الكورس، المسارات والإرشاد، البحث والإشعارات، وخدمة المساعدين المدفوعة. هذه قائمة توجيهية؛ تفاصيل النطاق في وثيقة المنتج.

Crow Store وCrow Hub وVS مخطط لها كميزات «قريباً». الترجمة والدبلجة والذكاء الاصطناعي العام مؤجلة؛ **تصحيح الأكواد ومراجعة اعتراضاته بالذكاء الاصطناعي استثناء مطلوب من البداية**. الغرف وStreak ما زال توقيت إطلاقهما وتفاصيلهما غير محسومين؛ لا تُدرج تلقائياً ضمن النسخة الأولى أو خارجها.

## 3. قواعد التعاون واعتماد الإجابات

- نناقش **سؤالاً واحداً في كل مرة** مع صاحب المشروع. يجوز للفريق إعداد عدة موضوعات، لكن لا نطلب منه الإجابة عن قائمة طويلة دفعة واحدة.
- نجمع مجموعة مترابطة من الإجابات، ثم نوثّقها ونراجعها ونحدّث العربية والإنجليزية دفعة واحدة.
- «نعم» بعد سؤال ذي خيارين ليست اختياراً واضحاً؛ يُطلب تحديد المقصود. عدم الإجابة ليس موافقة.
- عند سؤال «ما الأفضل؟» يقدم الفريق توصية وأسبابها وأثرها، وتظل مقترحاً إلى أن يعتمدها صاحب المشروع صراحة.
- إذا غيّر صاحب المشروع قراراً سابقاً، نحفظ التغيير ونزيل أثر القرار الملغى من القواعد والرحلات ومعايير القبول ونموذج البيانات.
- لا يُعاد طرح سؤال محسوم إلا لوجود تعارض جديد أو طلب مراجعة صريح. يمكن طلب تفاصيل لم تُحسم ضمن الموضوع نفسه.
- عبارة «من لوحة التحكم» لا تحدد وحدها من يملك الصلاحية، ولا نطاق الإعداد، ولا تاريخ نفاذه أو أثره على الاتفاقات القائمة؛ تُستكمل هذه الحدود عند الحاجة.
- توصيات المختصين مدخل للمراجعة؛ لا ننسب اعتماداً لصاحب المشروع أو دوراً لشخص من الفريق دون اتفاق.

| الحالة | معناها في سجل الفريق |
| --- | --- |
| متفق عليه | قرار صريح؛ قابل للمراجعة لاحقاً بقرار جديد موثّق. |
| مبدئي | اتجاه مقبول مع تفاصيل أو مراجعة نهائية معلّقة. |
| مقترح | توصية لم تُعتمد. |
| مفتوح | سؤال بلا جواب كافٍ. |
| مؤجّل | النقاش أو التنفيذ مؤجّل مع توضيح أيهما. |
| ملغى أو مستبدل | قرار سابق أُبطل؛ يبقى في التاريخ ولا يُستخدم كقاعدة حالية. |

## 8. توزيع العمل داخل الفريق — اقتراح قابل للتعديل

لم تُعيّن أسماء أو مسؤوليات فعلية بعد. يمكن لشخص واحد تغطية أكثر من دور، ويمكن تقسيم البحث داخلياً، مع منسق واحد يجمع الأسئلة لصاحب المشروع.

| المسار | المسؤول المقترح | المطلوب تسليمه |
| --- | --- | --- |
| تنسيق القرارات | منسق تحليل يختاره الفريق | جدول الأسئلة، محاضر الإجابات، تتبع التعارضات والتغييرات. |
| المحتوى وتجربة الطالب | محلل منتج مع ممثل تعليمي | سياسات التحديث والتقدّم والشهادة، ورحلات الطالب وحالاتها الاستثنائية. |
| الأموال والاتفاقات | محلل مع المختص المالي وصاحب المشروع | أمثلة حسابية للاسترداد والحجز والنقل والمساعدين، مع مدخلات ونتائج واضحة. |
| الصلاحيات والأمن | ممثل أمن مع محلل بيانات | مصفوفة وصول، إلغاء الصلاحيات، نطاق البيانات، التدقيق والخصوصية. |
| البيانات والبنية | مصمم بيانات ومعماري | نموذج منطقي وبدائل تقنية تستند إلى القرارات، مع فصل المقترح عن المعتمد. |
| مراجعة الوثائق واللغة | مراجع متطلبات ومراجع ترجمة | تطابق العربية والإنجليزية، صحة الروابط والمعرفات ومعايير القبول. |

الفريق يحضّر البدائل والآثار، وصاحب المشروع يحسم قواعد المنتج. تفاصيل الاعتماد الداخلي للمختصين تُتفق معه، ولا يفترض هذا الملف أسماء مخوّلين أو مواعيد تسليم ملزمة.

## 9. قالب تسجيل إجابة أو قرار

انسخ هذه البطاقة لكل سؤال. **تاريخ التوثيق منفصل عن تاريخ صدور الإجابة.** إذا لم تتوفر معلومة، اكتب «غير محدد» بدلاً من اختلاقها.

| الحقل | ما يسجله الفريق |
| --- | --- |
| المعرف | H-Qxx، وروابط O / D / H-D ذات الصلة. |
| السؤال المطروح | سؤال واحد بصياغة محددة، مع مثال عند الحاجة. |
| نص إجابة صاحب المشروع | النص أو اقتباس دقيق؛ رابط النقاش أو مرجعه المتاح. |
| تاريخ الإجابة والتوثيق | كل تاريخ مستقلاً؛ أو «غير محدد» إذا لم يُعرف. |
| الحالة | مفتوح / مقترح / مبدئي / متفق عليه / مؤجّل / مستبدل. |
| الصياغة التشغيلية | الفاعل، الشرط، الإجراء، والنتيجة، دون إضافة افتراضات. |
| القرار السابق المتأثر | معرفه والجزء الذي أُلغي أو قُيّد؛ «لا يوجد» إن لم يتأثر شيء. |
| الاستثناءات وما لم يُحسم | حدود القرار وأسئلة المتابعة الضرورية. |
| أثر البيانات والصلاحيات والمال | حقول أو حالات تحتاج نمذجة، بصفتها مقترحات حتى اعتمادها. |
| مثال قبول | «عند ... وإذا ... تكون النتيجة ...»؛ يعبّر عن سلوك مطلوب وليس اختباراً منفذاً. |
| المراجعة | معد البطاقة، المراجع، ومن اعتمد القرار فعلياً؛ لا تملأ بأسماء غير متفق عليها. |
| مواضع التحديث | الملفات والأقسام ومعايير القبول المتأثرة في اللغتين. |

مثال محسوم: طلب استرداد قُدِّم في اليوم السادس وظل دون معالجة حتى اليوم الثامن. **النتيجة المطلوبة:** لا يُرفض لتأخر الإدارة، ولا تتحرر أموال هذه العملية قبل حسمه. **ما لا نستنتجه:** أن الاسترداد مقبول تلقائياً، أو أن مهلة مراجعة محددة اعتُمدت.

## 10. مخرجات الدفعة التالية ومعيار جاهزيتها

الدفعة التالية ليست «الإجابة عن كل شيء». اختر مجموعة مترابطة؛ بداية مناسبة هي المحتوى والتقدّم ثم الاسترداد والنقل، مع الاحتفاظ بقائمة بقية الأسئلة.

1. **تسوية الإصدار 0.2:** دمج قرارات القسم 4 ومعالجة كل موضع في القسم 5؛ إعطاء الإصدار التالي رقمه وتاريخه عند إتمامه فعلياً.
2. **سجل إجابات:** بطاقة لكل قرار جديد، وربط القرارات المستبدلة ببدائلها والأسئلة المفتوحة بنقطة المتابعة.
3. **مصفوفة صلاحيات محدثة:** قبل نقل الملكية وبعده، وخلال خدمة المساعد وتعليقها وإنهائها، مع نطاق كل لوحة.
4. **سيناريوهات قبول:** شراء كامل دون خصم للمحتوى المشترك، تحديث مجاني، درس منقول مع حق محفوظ، طلب استرداد متأخر المعالجة، ونقل أثناء الحجز.
5. **أثر بيانات مقترح:** العلاقات والحالات والتاريخ المالي والتقدّم؛ لا SQL أو Migrations نهائية قبل اعتماد النموذج.
6. **نسختان متطابقتان:** مراجعة العربية والإنجليزية، ثم توليد HTML والتحقق من الروابط والفهرس، ثم رفع دفعة موثقة إلى فروع التخطيط.

تُعد الدفعة جاهزة للمراجعة عندما لا تتعارض قواعدها النشطة، ولكل قرار مصدر وحالة وأثر، وكل سؤال غير مجاب ظاهر بوضوح. لا يشترط إغلاق ميزات المستقبل لاعتماد نطاق مستقر، ولا يجوز إعلان اكتمال تخطيط كل قواعد البيانات بينما أسئلة مؤثرة ما زالت مفتوحة.

## 11. التعامل مع المستودع والتسليم بين أعضاء الفريق

| الفرع | دوره |
| --- | --- |
| plan | المرجع العربي الأصلي الدائم للخطط. |
| plan-ar | نسخة عربية مطابقة لـplan عند نشر الدفعة، إلى نفس commit. |
| plan-en | ترجمة إنجليزية كاملة للدفعة نفسها؛ تتطابق القرارات والمعرفات ولا تتطابق لغة الملفات. |
| docs | توثيق رسمي بعد مراجعة واعتماد، وليس نسخة تلقائية من مسودات التخطيط. |
| develop / staging / main | التطوير والاختبار والإنتاج؛ لا تُنقل إليها مسودات التخطيط كاملة. |

قاعدة العمل المعتمدة: لا حذف للفروع الدائمة ولا force push. لا دمج مباشر بين فرعي اللغات يستبدل لغة بأخرى. مزامنة اللغتين مراجعة وترجمة وليست عملية آلية.

**أسلوب تعاون مقترح:** يبدأ كل موضوع من أحدث plan في فرع مهمة مؤقت مثل `planning/content-progress`، وتُراجع مادته بطلب دمج إلى plan. يحدد الفريق من ينسق تحديث plan-ar والترجمة إلى plan-en؛ لا يحرّر عدة أشخاص القسم نفسه دون تنسيق. هذا اقتراح لتنظيم الفريق، وليس ادعاءً بإضافة شرط حماية جديد على GitHub.

عند كل تسليم داخلي: اذكر السؤال الأخير وإجابته، والسؤال التالي، والملفات المعدلة، وما لم يُرفع، ومرجع النسخة العربية التي تُرجمت. إذا لم تكتمل الترجمة، أعلن ذلك بوضوح ولا تصف الفروع بأنها متزامنة.
